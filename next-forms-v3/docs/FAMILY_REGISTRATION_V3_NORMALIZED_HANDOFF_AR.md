# المخرج العملي المعتمد — Family Registration v3 (نسخة عائلية مُطبَّعة على البيانات القديمة)

## القرار
**لا نعتمد `student-registration-packet` كبديل مباشر لـ `family-registration.html`** في هذه الحالة.

السبب:
- `student-registration-packet` مناسب أكثر لملف طالب واحد مطبوع
- بينما `family-registration.html` القديم مبني على **إدخال بيانات الأسرة مرة واحدة** ثم إضافة عدة أبناء
- والمطلوب الجديد من المستخدم هو:
  - الاحتفاظ بمنطق الفورم القديم كمصدر معلومات
  - إعادة ترتيبه في النسخة الجديدة
  - **منع تكرار بيانات الأب/ولي الأمر مع كل طالب**

لذلك المخرج الصحيح هو:
## **بناء مسار جديد مستقل داخل `next-forms-v3` باسم `family-registration-v3`**

---

# الهدف الوظيفي
إنشاء استمارة جديدة حديثة لكن مطابقة منطقيًا للنسخة القديمة، بحيث:
- بيانات ولي الأمر تُكتب **مرة واحدة فقط**
- بيانات الأم تُكتب **مرة واحدة فقط**
- اسم العائلة يُكتب **مرة واحدة فقط**
- كل طالب يُضاف كبطاقة مستقلة داخل نفس الطلب
- الحقول الموروثة من الأب/العائلة تُملأ تلقائيًا مع إمكانية التعديل عند الحاجة
- الإخراج النهائي يدعم:
  - حفظ draft
  - submit عبر RPC
  - طباعة نسخة عائلية
  - توليد نسخة/ملف فرعي لكل طالب إذا لزم

---

# القاعدة الأساسية الجديدة
بدل الحقل القديم في بعض النماذج:
- `father_full_name`

نعتمد بنية مفصّلة:
- `guardian_given_name`
- `guardian_father_name`
- `family_name`

### لماذا؟
لأن المستخدم يريد:
- الاسم + اسم الأب + العائلة
- بدون إعادة كتابة نفس المعلومات عند تسجيل أكثر من ابن

## 3) قسم الطلاب — بطاقة متعددة داخل نفس الطلب
كل طالب له بطاقة مستقلة، لكن لا نكرر بيانات العائلة.

### لكل طالب
#### حقول أساسية
- اسم الطالب
- اسم الأب
- العائلة
- الاسم الكامل المحسوب
- تاريخ الميلاد
- الجنس
- الصف
- الشعبة
- مكان الولادة
- رقم الجواز
- انتهاء الجواز
- المدرسة السابقة
- عنوان السكن في مشهد
- عنوان السكن في العراق
- صورة الطالب

### القاعدة الأهم
لكل طالب نعتمد ثلاث طبقات:
1. **قيمة افتراضية موروثة من الأسرة**
2. **إمكانية تعديلها لكل طالب عند الحاجة**
3. **حقل Full Name محسوب تلقائيًا**

### مثال عملي
#### يُكتب مرة واحدة في قسم ولي الأمر:
- `guardian_given_name = علي`
- `guardian_father_name = كاظم`
- `family_name = حسن`

#### عند إضافة طالب جديد
يمتلئ تلقائيًا:
- `student_father_name = علي`
- `student_family_name = حسن`

ويبقى المستخدم فقط يكتب مثلًا:
- `student_given_name = محمد`

فيصبح:
- `student_full_name = محمد علي حسن`

### وإذا كان هناك استثناء؟
إذا كان الطالب يحتاج اسمًا مختلفًا أو guardian ليس الأب، تبقى الحقول قابلة للتعديل يدويًا.

### حقول مقترحة لكل طالب
- `student_given_name`
- `student_father_name` ← default من ولي الأمر
- `student_family_name` ← default من العائلة
- `student_full_name` ← computed / overridable
- `student_birth_date`
- `student_gender`
- `student_class_id`
- `student_section`
- `student_birth_place`
- `student_passport_number`
- `student_passport_expiry_date`
- `student_previous_school`
- `student_address_mashhad`
- `student_address_iraq`
- `student_photo`
- `student_username`
- `student_initial_password`

## 4) قسم صحي/عائلي مشترك
يُحفظ مرة واحدة على مستوى الطلب أو مرة لكل طالب بحسب الحاجة.

### الحد الأدنى المقترح
- `living_with_in_iran`
- `general_family_health_notes`
- `document_notes`

### وحقل اختياري لكل طالب
- `student_health_notes`

### لماذا؟
لأن بعض البيانات الصحية عامة للأسرة، وبعضها خاص بطالب واحد.

---

## 5) قسم مالي عائلي
بدل إعادة قسم مالي لكل طالب، نجعله على مستوى الأسرة مع ربط اختياري لكل دفعة بمن يخصه.

### الحقول
- لائحة الرسوم المعتمدة
- دفعات متعددة
- مجموع كلي
- ربط الدفعة بـ:
  - الأسرة ككل
  - طالب محدد

### حقول مقترحة للدُفعات
- `payment_row_id`
- `student_ref` (nullable)
- `card_number`
- `tracking_number`
- `reference`
- `payment_date`
- `amount`
- `notes`

### النتيجة
- دفعة عامة للأسرة
- أو دفعة مرتبطة بطالب بعينه
- بدون تكرار الجداول

---

## 6) قسم الوثائق
على مستوى الأسرة أو الطالب:
- استلام استنساخ الوثيقة
- استلام النسخة الأصلية
- ملف صحي
- مرفقات داعمة

### الأفضل عمليًا
- document status عام للأسرة
- مرفقات خاصة قابلة للربط بكل طالب عند الحاجة

## 7) الطباعة

- وطباعة منظمة
- وإمكانية حفظ نسخة عامة للأسرة + صفحة لكل طالب في ملفه

# قواعد UX المعتمدة

## 1) تقليل التكرار
- اسم العائلة يُدخل مرة واحدة
- اسم الأب لا يتكرر يدويًا في كل بطاقة إلا عند override
- بيانات الاتصال لا تتكرر داخل بطاقات الطلاب

## 2) الوضوح
- كل بطاقة طالب تظهر:
  - الاسم الكامل النهائي
  - هل الحقول inherited أم معدلة يدويًا

## 3) المرونة
- أي قيمة موروثة يمكن فك ارتباطها وتعديلها لطالب محدد

## 4) الطباعة
- Preview مطابق تقريبًا للنسخة النهائية
- نسخة الأسرة ونسخة الطالب منفصلتان منطقيًا

# ما الذي نحتفظ به من القديم؟
نحتفظ من `family-registration.html` كمرجع معلوماتي:
- تقسيم ولي الأمر / الأم / الطلاب
- تعدد الطلاب في نفس الطلب
- توليد اسم المستخدم وكلمة المرور
- المنطق العائلي
- خيارات الجنسية/التحصيل/العمل/الإقامة
- حقول الجواز وتواريخه
- الصورة
- الطباعة

## وما الذي نغيّره؟
- نلغي تكرار بيانات الأب داخل كل طالب
- نفصل الاسم الثلاثي إلى مكونات
- نجعل القيم inherited + editable
- نربط القسم المالي بالعائلة
- نحول كل الكتابة إلى RPC-only
- نجعل UX حديثًا وواضحًا

# خطة التنفيذ العملية الموصى بها
## المرحلة 1 — اعتماد الموديل
- اعتماد schema الجديدة العائلية
- اعتماد الحقول المفصلة لولي الأمر والأم
- اعتماد `students[]` كبطاقات متعددة

## المرحلة 2 — بناء الواجهة
- صفحة `family-registration-v3`
- بطاقات الطلاب الديناميكية
- auto-fill من بيانات ولي الأمر والعائلة
- full-name computed preview

## المرحلة 3 — RPC وSQL
- submit RPC جديد خاص بالعائلات
- حفظ family header + students children + payments + attachments
- list/review مناسب للطلبات العائلية

## المرحلة 4 — الطباعة
- نسخة عائلية رئيسية
- ملحق طالب/طلاب

## المرحلة 5 — الربط
- بعد نجاح UAT، نربط `family-registration.html` بهذا المسار الجديد وليس بـ `student-registration-packet`

# الخلاصة التنفيذية
**المخرج العملي المتكامل** هو:
1. الإبقاء على الفورم القديم كمصدر مرجعي للمعلومات
2. عدم الاكتفاء بتجميل الفورم المطبوع الحالي
3. بناء **Family Registration v3** كنموذج عائلي حقيقي
4. تفصيل اسم ولي الأمر إلى:
   - الاسم
   - اسم الأب
   - العائلة
5. توريث هذه المعلومات تلقائيًا لبطاقات الأبناء
6. جعل كل بطاقة ابن تحتاج فقط بياناتها الخاصة، لا تكرار بيانات الوالد
7. إخراج مطبوع منظم للأسرة ولكل طالب
